**스프링 내부구조**

스프링은 스프링 컨테이너라고 불리는 스프링 런타임 엔진을 제공한다. **설정정보**를 참고해서 어플리케이션을 구성하는 오브젝트를 생성하고 관리한다. 보통 웹 모듈에서 동작하는 서비스나 서블릿으로 등록해서 사용한다. 

스프링의 프로그래밍 모델은 **IoC/DI, PSA, AOP** 세가지 핵심 모델을 지원한다. 이 세가지 모델을 활용해서 개발을 하면 POJO프로그래밍을 달성할 수 있다.

**Plain Old Java Object**
	특정 자바모델, 기능, 환경, 규약, 라이브러리 등을 따르지 않고 의존적이지 않은 자바 오브젝트를 의미한다.
	예외 ) 스프링을 관리하는 재단에서 허용한 기술은 사용해도 POJO방식에 위반되지 않는다.

**POJO규칙**
	1. Java나 Java스펙에 정의된 것 외에는 기술적, 규약에 얽매이지 않아야한다.
		예시 - getter, setter는 특정 기술에 의존적이지 않기 때문에 위반되지 않는다. ( 위반 X)
		특정 기술을 상속받아 작성한다면 명시적으로 작성한 부분을 수정해야 할수도 있다. 
		( 위반 O )
	2. 특정 환경에 종속되지 않아야 한다.
		예시 - Tomcat의 API를 사용해서 개발후에 Zetty로 변경 요청이 들어온다면 TomcatAPI소스를 전부 다 걷어야 할 수도 있다. ( 위반 O )

**POJO방식을 사용하는 이유**
	1. 특정 환경이나 기술에 종속적이지 않으면 재사용 가능하고, 확장 가능한 유연한 코드를 작성할 수 있다.
	2. 저 수준 레벨의 기술과 환경에 종속적인 코드를 애플리케이션 코드에서 제거 함으로써 코드가 깔끔해진다.
	3. 코드가 깔끔해지기 때문에 디버깅 하기도 상대적으로 쉽다.
	4. 특정 기술이나 환경에 종속적이지 않기 때문에 테스트 역시 단순해진다.
	5. **객체지향적인 설계를 제한없이 적용할 수 있다.(가장 중요한 이유)**

**IoC(Inversion of Control)**
	스프링에서는 프로그램의 흐름을 프레임워크가 주도하는데, 객체의 생성, 생명 주기를 개발자가 아니라 프레임워크가 주도하기 때문에 제어권이 넘어갔으므로 **제어의 역전** 이라 한다.
	**DI** 도 제어권을 프레임워크가 통제하게 되면서 가능해진다
	
**제어역전 과정**
	1. 객체생성
	2. 의존성 객체 주입 ( 스프링이 생성한 객체를 외부에서 주입 )
	3. 의존성 객체 메소드 호출
	
	이렇게 생성된 객체는 스프링에서 Bean이라고 부른다. 스프링이 실행될때 생성되고, 필요한 곳에
	주입된다. 이 객체들은 컨테이너에서 싱글톤으로 관리된다.

**DI(Dependency Injection)**
	의존성 주입이라는 의미로, 객체를 직접 생성하는 것이 아니라 외부에서 생성한 후 주입 시켜주는 방법을 말한다.
	DI방식을 이용하면, 확장은 용이하고, 변경에는 닫혀있어 재사용이 가능하다.

**DI를 하는 세가지 방법**

1. Setter Injection( setter메서드 주입 )
```java
	// setter 메서드를 통한 의존 주입
	public class MemberService { private
		MemberRepository memberRepository;
		
		@Autowired // 없어도 됨 public void 
		setMemberRepository(MemberRepository memberRepository) {
			 this.memberRepository = memberRepository; 
		}
	}
```

2. Field Injection( 필드 주입 )
```java
// 필드에 애노테이션을 붙여 의존 주입
public class MemberService {
	@Autowired
	private MemberRepository memberRepository;
}
```

3. Constructor Injection( 생성자 주입 )
```java
// 생성자를 통한 의존 주입
@RequiredArgsConstructor //final이 붙은 필드에 생성자를 만들어줌, 이 애노테이션만 붙여도 의존 주입이 가능함
public class MemberService {
	private final MemberRepository memberRepository;
	// RequiredArgsConstructor 애노테이션을 붙이면 주석처럼 생성자를 만들지 않아도 됨 
	//@Autowired 생성자가 하나 있을 때 스프링이 알아서 등록을 해줌
	/*public MemberService(MemberRepository memberRepository) { 
		this.memberRepository = memberRepository;
	}*/
}
```

스프링을 포함한 DI방식의 프레임워크는 **생성자 주입** 을 권장한다. 객체의 불변성을 보장하고, 테스트 용이, 코드 작성이 간결, 순환 참조 에러를 방지할 수 있기 때문이다.

**AOP(Aspect Oriented Programming)**
	관점 지향 프로그래밍이라는 의미로, 어떤 로직을 기준으로 **핵심적인 관점, 공통적인 관점(부가적인 관점)으로 나누어서 보고** 그 관점을 기준으로 모듈화하겠다는 의미이다.
	AOP는 공통된 기능을 재사용하는 방식이다.
	AOP를 하면 다음과 같은 이점을 얻을 수 있다.

	1. 코드의 간결성 유지
	2. 객체 지향 설계 원칙에 맞는 코드 구현
	3. 코드의 재사용


**PSA(Portable Service Abstraction)**
	**하나의 추상화로 여러 서비스를 묶어둔 것**, 환경의 변화와 관계없이 일관된 방식으로 기술에 접근할 수 있는 환경을 제공하려는 추상화 구조를 말한다.
